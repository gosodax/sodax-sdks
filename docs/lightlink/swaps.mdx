SODAX swaps are intents, not bridges. Your user signs one transaction on LightLink that locks the input and declares what they want on the destination network. Solvers fill it; the SODAX relayer carries proof between LightLink, the hub (Sonic), and the destination. If nothing fills, the intent can be cancelled and funds recovered.

From your side it is one SDK call. From your user's side it is one wallet prompt, plus an approval the first time they swap an ERC-20 token.

## What this looks like on LightLink

- **Source**: the intent transaction is an ordinary EVM transaction on LightLink Phoenix mainnet, signed by the user's wallet and paid for in ETH. `ChainKeys.LIGHTLINK_MAINNET` (`'lightlink'`) identifies the network everywhere in the SDK.
- **Reach**: any solver-compatible asset on any SODAX network is a valid destination, <span data-sodax-config="count" data-metric="swap-tokens">166</span> assets today. The [on-LightLink asset list](/lightlink/networks-and-assets) only bounds what users hold on LightLink itself, not what they can swap into.
- **Tokens**: ETH uses the zero address; every other token, LL and the `.LL` tokens included, is a LightLink ERC-20 contract. Every `.LL` token uses 18 decimals. Read addresses and decimals from the SDK config rather than copying them.
- **Settlement**: output lands on the destination network at `dstAddress`. Swaps into LightLink settle as ordinary ETH or ERC-20 balances at the recipient's LightLink address, with no extra step on the receiving side.

## Approvals {#approvals}

`swap()` does not approve the input token for you. ETH is the native token and needs no approval. Every ERC-20 does: SODAX's asset manager pulls it through the token's ERC-20 interface, so check the allowance first and approve when it falls short.

```typescript
const allowance = await sodax.swaps.isAllowanceValid({ params, walletProvider });
if (!allowance.ok) throw allowance.error;

if (!allowance.value) {
  const approval = await sodax.swaps.approve({ params, walletProvider });
  if (!approval.ok) throw approval.error;
  // wait for the approval to be mined before calling swap()
}
```

`params` is the same intent params object you pass to `swap()`. The approval is a LightLink transaction too, so it also costs the user a little ETH in gas.

## Quoting

The solver API quotes both directions:

```typescript
const quoteResult = await sodax.swaps.getQuote({
  token_src: eth.address,             // token on LightLink
  token_dst: usdc.address,            // token on the destination network
  token_src_blockchain_id: ChainKeys.LIGHTLINK_MAINNET,
  token_dst_blockchain_id: ChainKeys.ARBITRUM_MAINNET,
  amount: 10n ** BigInt(eth.decimals) / 10n, // 0.1 ETH
  quote_type: 'exact_input',          // the only supported quote type
});
```

`getQuote` deducts any configured partner fee before quoting, so `quoted_amount` is the net output the user actually receives.

## Fees

Using SODAX is free to integrate. Two fees can apply to a trade:

- **Base fee**: a fixed 0.1% of the input, taken by the protocol. Not configurable; compute it ahead of time with `getSolverFee(inputAmount)`.
- **Your fee**: optional platform fee on top, set by you and paid to you. It is the only fee you control. Configure it at SDK setup and check it with `getPartnerFee(inputAmount)`. See [Monetize SDK](/developers/how-to/monetize_sdk).

The user also pays LightLink's network fee for the intent transaction, in ETH. LightLink's [Enterprise Mode](https://docs.lightlink.io/lightlink-protocol/building-on-lightlink/enterprise-mode-overview) zero-fee transactions apply to contracts a project registers and pays for; the SDK does not send SODAX transactions that way.

## Executing

Prefer `swap()`. It creates the intent on LightLink, verifies it landed, submits it to the relay, waits for the packet on the hub, and notifies the solver. The [Quickstart](/lightlink/quickstart#4-quote-and-swap) has the complete call. Track progress with `getStatus(request)`, and cancel unfilled intents with `cancelIntent`. Limit orders (intents without deadlines) work from LightLink too, via `createLimitOrder`.

Orchestrating manually with `createIntent` and `submitIntent` works the same as on any EVM network: LightLink intents need no relay extra data.

## Error handling

Operations return `Result<T>` instead of throwing. The core methods (`swap`, `createIntent`, `postExecution`) return a typed `SodaxError` union you can `switch` on by `error.code`.
