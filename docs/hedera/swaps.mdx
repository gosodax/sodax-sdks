SODAX swaps are intents, not bridges. Your user signs one transaction on Hedera that locks the input and declares what they want on the destination network. Solvers fill it; the SODAX relayer carries proof between Hedera, the hub (Sonic), and the destination. If nothing fills, the intent can be cancelled and funds recovered.

From your side it is one SDK call. From your user's side it is one wallet prompt, plus an approval the first time they swap an HTS token.

## What this looks like on Hedera

- **Source**: the intent transaction is an EVM transaction sent through Hedera's JSON-RPC relay and signed by the user's ECDSA key. `ChainKeys.HEDERA_MAINNET` (`'hedera'`) identifies the network everywhere in the SDK.
- **Reach**: any solver-compatible asset on any SODAX network is a valid destination, <span data-sodax-config="count" data-metric="swap-tokens">166</span> assets today. The [on-Hedera asset list](/hedera/networks-and-assets) only bounds what users hold on Hedera itself, not what they can swap into.
- **Tokens**: Hedera assets are native HTS tokens, addressed by the EVM form of their token ID. USDC is token `0.0.456858`, which the SDK lists as `0x000000000000000000000000000000000006f89a`. Read addresses from the SDK config; never convert them by hand.
- **Settlement**: output lands on the destination network at `dstAddress`. Swaps into Hedera settle as HTS balances on the recipient's EVM address, which must already be associated with the token: see [Receiving tokens on Hedera](#receiving-tokens-on-hedera).

## Approvals {#approvals}

`swap()` does not approve the input token for you. HBAR is the native token and needs no approval. Every HTS token does: SODAX's asset manager pulls it through the token's ERC-20 interface, so check the allowance first and approve when it falls short.

```typescript
const allowance = await sodax.swaps.isAllowanceValid({ params, walletProvider });
if (!allowance.ok) throw allowance.error;

if (!allowance.value) {
  const approval = await sodax.swaps.approve({ params, walletProvider });
  if (!approval.ok) throw approval.error;
  // wait for the approval to be mined before calling swap()
}
```

`params` is the same intent params object you pass to `swap()`.

## Quoting

The solver API quotes both directions:

```typescript
const quoteResult = await sodax.swaps.getQuote({
  token_src: hbar.address,            // token on Hedera
  token_dst: usdc.address,            // token on the destination network
  token_src_blockchain_id: ChainKeys.HEDERA_MAINNET,
  token_dst_blockchain_id: ChainKeys.ARBITRUM_MAINNET,
  amount: 10n * 10n ** BigInt(hbar.decimals), // 10 HBAR
  quote_type: 'exact_input',          // the only supported quote type
});
```

`getQuote` deducts any configured partner fee before quoting, so `quoted_amount` is the net output the user actually receives.

## Fees

Using SODAX is free to integrate. Two fees can apply to a trade:

- **Protocol fee**: 0.01% to 0.1% of the input, depending on the route the solver takes. It is already included in the quote, along with the gas cost of delivering the tokens. `getSolverFee(inputAmount)` returns the maximum (0.1%).
- **Your fee**: optional platform fee on top, set by you and paid to you. It is the only fee you control. Configure it at SDK setup and check it with `getPartnerFee(inputAmount)`. See [Monetize SDK](/developers/how-to/monetize_sdk).

The user also pays Hedera's network fee for the intent transaction, in HBAR, like any other Hedera EVM transaction.

## Executing

Prefer `swap()`. It creates the intent on Hedera, verifies it landed, submits it to the relay, waits for the packet on the hub, and notifies the solver. The [Quickstart](/hedera/quickstart#4-quote-and-swap) has the complete call. Track progress with `getStatus(request)`, and cancel unfilled intents with `cancelIntent`. Limit orders (intents without deadlines) work from Hedera too, via `createLimitOrder`.

Orchestrating manually with `createIntent` and `submitIntent` works the same as on any EVM network: Hedera intents need no relay extra data.

## Receiving tokens on Hedera {#receiving-tokens-on-hedera}

On most EVM networks any address can receive any token. On Hedera an account receives an HTS token only if it is **associated** with that token. This applies whenever Hedera is the destination: a swap into Hedera, or a money market borrow or withdraw delivered to Hedera. HBAR itself needs no association.

For a SODAX delivery the association must already exist. A free or unlimited **automatic association** slot is not enough, even though Hedera would use one for an ordinary transfer: using it during delivery costs more gas than the relay's delivery execution provides, so the delivery fails. Accounts auto-created at an EVM address have unlimited slots, so most EVM-wallet users still need to associate each HTS token once before their first delivery of it.

The SDK checks this for you. Before signing, it refuses a delivery of an HTS token to a Hedera account that cannot receive it, with `context.reason` set to `hedera-<reason>`. Check the recipient yourself to offer the fix first:

```typescript
const readiness = await sodax.spoke.hedera.checkDestination({ address: dstAddress, token: usdc.address });

if (!readiness.ready && readiness.reason === 'not_associated') {
  // Associates exactly this token, signed by the account that will receive it
  const association = await sodax.spoke.hedera.requestAssociation({
    srcAddress: dstAddress,
    token: usdc.address,
    walletProvider, // an EVM wallet provider connected to dstAddress on Hedera
  });
  if (!association.ok) throw association.error;
}
```

`requestAssociation` calls `associate()` on the token's own address ([HIP-719](https://hips.hedera.com/hip/hip-719)), so it associates that one token and nothing else. The account pays the network fee in HBAR. It resolves once the association is mined and the mirror node shows it. Pass `raw: true` to get the unsigned call instead.

| `reason` | What it means | Who fixes it |
| - | - | - |
| `not_associated` | The account is not associated with the token | The account owner, with `requestAssociation` |
| `account_missing` | No Hedera account exists at the address yet | The owner: create the account (send it HBAR), then associate |
| `frozen` | The token froze this account | The token's freeze authority |
| `kyc_not_granted` | The token requires a KYC grant the account lacks | The token's KYC authority |

The check reads Hedera's public mirror node (`https://mainnet-public.mirrornode.hedera.com`); set `chains.hedera.mirrorNodeUrl` in the SDK config to use another. If the mirror node cannot be read, the check throws and the SDK refuses the delivery rather than send one that may fail.

In React, `useSwapLifecycle` from `@sodax/dapp-kit` runs this as its `hederaAssociation` setup step. The wallet must be on Hedera for the association. Pass `dstChainSwitch` from a second `useEvmSwitchChain` for the destination: the lifecycle shows `needsChainSwitch`, `next()` switches to Hedera, then associates, and the source `chainSwitch` brings the wallet back before the swap. Without `dstChainSwitch`, a wallet provider that can report and switch its chain (the `@sodax/wallet-sdk-core` EVM provider) switches itself to Hedera on the first `next()` and sends the association on the next one; a refused switch comes back from `next()` as a failed `Result`. `hederaBlocked` reports the other reasons in `lifecycle.hedera.blockedReason`.

## Error handling

Operations return `Result<T>` instead of throwing. The core methods (`swap`, `createIntent`, `postExecution`) return a typed `SodaxError` union you can `switch` on by `error.code`.
